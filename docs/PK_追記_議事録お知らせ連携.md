## 【挿入A】§8「議事録機能」の末尾(「### 監査ログ」の直後)に追加

```
### お知らせへの自動連携(確定)
議事録の投稿を部会員に知らせるため、**議事録の投稿時にお知らせを自動生成**する。
議事録側に既読管理を作り込まず、既存のお知らせの既読管理(`announcement_reads`)に一本化するため。

- **生成タイミングは初回投稿時のみ**。編集のたびに通知が飛ぶのを防ぐ
- お知らせ本文は定型文＋議事録タイトル＋議事録詳細ページへの直リンク
- お知らせ一覧には**「議事録」カテゴリバッジ**を表示(既存の 全体/個人選果/共同選果 に並ぶ)
- 議事録の投稿にあたって、管理者が別途お知らせ投稿画面を開く必要はない

#### カテゴリ別の配信先(確定)
役員協議会の議事録は一般ユーザーに見せないため、由来するお知らせも同じ制御をかける。
**LINE配信先もカテゴリで振り分ける**点に注意(部会員グループへ流すと議事録の権限制御が無意味になる)。

| 議事録カテゴリ | サイト表示 | LINE配信先 |
|---|---|---|
| 全体協議会 | 全員 | 部会員のLINEグループ(10分保留後) |
| 役員協議会 | 管理者のみ | 管理者用LINEグループチャット(10分保留後) |

- 管理者用LINEグループは、§6「投稿があった時点で管理者用グループへ自動通知」で
  既に通知先として設計済み。追加のインフラは不要

#### 議事録由来のお知らせの取り扱い(確定)
議事録由来のお知らせは**議事録に紐づく従属データ**であり、独立した投稿ではない。
そのため手動投稿のお知らせとは操作系を分ける。

| 操作 | 結果 |
|---|---|
| 議事録を投稿 | お知らせを自動生成し、10分の保留を開始 |
| 保留中に議事録を編集 | お知らせの文面(タイトル・リンク)も追従し、**保留時間をリセット** |
| 議事録を削除 | 紐づくお知らせも連動して取り下げ |
| お知らせ側の個別削除 | **ボタンを出さない**(消す場合は議事録側から操作する) |

- 保留中の編集で保留時間がリセットされるのは、手動投稿の「訂正すると保留時間リセット」と同じ考え方
  (→ §6 投稿画面のUI)。タイトルの誤字に気づいた際、議事録ごと作り直さずに済むようにするため
- 議事録を削除しても、お知らせ・議事録とも**論理削除**とし、監査ログは残す(→ §1 データ整合性の原則)
```

## 【挿入D】§3「権限」の末尾に追記(本番実装時の注意)

モック実装での割り切りと、本番で必須になる対応を明記する。

```
#### モックと本番の差異(実装時の必須事項)
モックでは利便性のため以下の割り切りをしている。**本番実装ではいずれもサーバー側で行うこと**。

- **役割(管理者/一般)の保持**:モックは`localStorage`。利用者が書き換え可能なため、
  本番は**サーバー側のセッションで判定**する
- **管理者専用ページへの直接アクセス**:モックはURLを直接叩けば一般ユーザーでも開ける
  (例:`minutes-edit.html`)。本番は**サーバー側で権限チェックしてリダイレクト**する
- **役員協議会の非表示**:モックは画面側のフィルタ。本番は**クエリ段階で除外**する
  (一覧・検索・詳細の直リンクすべてが対象。詳細は議事録IDを直接指定されても弾くこと)
- **下書きの保存先**:モックは`localStorage`(`announce.html`/`minutes-edit.html`)。
  本番は**サーバー側の下書き保存**とする(→ §4 途中保存)
```
